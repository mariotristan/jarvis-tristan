Guide · Windows

T.R.I.S.T.A.N. in a Windows terminal.

A tristan command whose target is Windows 10 and 11 (x64); so far CI has run it only on Windows Server 2025. It is released in 0.6.1 as an installer and a portable zip. Run a mission on any of the five providers and approve each action in Windows Terminal, PowerShell or cmd. This page covers how to use it, how we ported it, what is proven and what is not, what comes next, and how we built it.

Released as 0.6.1, with an installer. Release v0.6.1 (7 November 2026) carries Tristan-0.6.1-windows-x64-setup.exe (21,201,665 bytes), the portable zip Tristan-0.6.1-windows-x64.zip, the Mac DMG, and a .sha256 file for each. The installer is the recommended download; the zip stays for people who want no install. Neither is code-signed, so Windows SmartScreen may warn when you run it; that has not been checked on a real Windows desktop. Only silent installs ran in CI, and nobody has clicked through the wizard screens. Running either on a Windows 10 or 11 desktop, and every provider against a live account, are still unverified: see What is supported. Download for Windows, or build from source.

Part 1

Install and first run

The Windows version is a terminal program, not a window. It runs the same agent loop, providers and approval rules as the Mac app, and asks you about each action in the terminal.

Download and verify

Get Tristan-0.6.2-windows-x64-setup.exe (21,198,312 bytes) and Tristan-0.6.2-windows-x64-setup.exe.sha256 from the latest release. It is an Inno Setup 6.7.3 setup.exe. It installs per user by default, into %LocalAppData%\Programs\Tristan, without administrator rights. It installs for all users when you choose that in the dialog or pass /ALLUSERS. It offers a task, Add Tristan to my PATH, ticked by default and removed again when you uninstall. It installs exactly the files that are in the zip: tristan.exe, the Swift runtime DLLs, LICENSE.txt, README.txt and THIRD-PARTY-NOTICES.txt. The checksum files were downloaded and checked with shasum -a 256 -c on a Mac; that is the same hash you compare below (upper or lower case does not matter).

# PowerShell, in the folder you downloaded to. Use the version you downloaded.
$setup = 'Tristan-0.6.2-windows-x64-setup.exe'

# 1. Check the download: the two hashes must be the same
(Get-FileHash -Algorithm SHA256 $setup).Hash
Get-Content "$setup.sha256"

# 2. Run it. Leave "Add Tristan to my PATH" ticked, then open a new terminal
.\$setup

The setup is not code-signed, so Windows SmartScreen or your antivirus may warn about it. We have not seen what a real Windows desktop shows, so we cannot tell you which button to press; if you trust the download (the checksum matched), choose to run it anyway. Signing is on the roadmap.

Silent install, for scripts. The switches are /VERYSILENT /SUPPRESSMSGBOXES /NORESTART, /CURRENTUSER or /ALLUSERS, /DIR="...", /TASKS="addtopath" and /LOG="...":

.\Tristan-0.6.2-windows-x64-setup.exe /VERYSILENT /CURRENTUSER /TASKS="addtopath"

This is the path CI exercises: silent installs only, on Windows Server 2025. The wizard screens have not been clicked through.

Portable, no install: the zip

Get Tristan-0.6.2-windows-x64.zip (30,224,533 bytes) and Tristan-0.6.2-windows-x64.zip.sha256 from the same release. The zip holds 23 files, about 80 MB unpacked: tristan.exe, the Swift runtime and Foundation DLLs, ICU, the Visual C++ runtime DLLs (MSVCP140, VCRUNTIME140, VCRUNTIME140_1), LICENSE.txt, THIRD-PARTY-NOTICES.txt and README.txt. Keep all the files in one folder.

# PowerShell, in the folder you downloaded to
$zip = 'Tristan-0.6.2-windows-x64.zip'

# 1. Check the download: the two hashes must be the same
(Get-FileHash -Algorithm SHA256 $zip).Hash.ToLower()
Get-Content "$zip.sha256"

# 2. Unpack it, for example into your own Programs folder
$dir = "$env:LOCALAPPDATA\Programs\Tristan"
Expand-Archive $zip -DestinationPath $dir

# 3. Put it on your PATH (your user only), then open a new terminal
[Environment]::SetEnvironmentVariable('Path', [Environment]::GetEnvironmentVariable('Path', 'User') + ";$dir", 'User')

First run

tristan --version     # 0.6.2 for this release; a development build says 0.0.0-dev
tristan providers     # which providers are ready, and what to set for the others
tristan --help

tristan providers prints one line per provider: ready, or not ready: with the fix. It checks that tools are present and settings look right. It does not check that you are logged in.

# for example, on a machine with only Ollama running
claude   not ready: the claude CLI was not found on PATH (install Claude Code)
copilot  not ready: the copilot CLI was not found on PATH (npm install -g @github/copilot)
bedrock  not ready: the AWS CLI was not found on PATH
azure    not ready: set the endpoint and deployment first: `tristan config set azure.endpoint <url>` and `tristan config set azure.deployment <name>`
ollama   ready

Set up each provider

Windows has no Configuration window, so two commands do its job. tristan config changes the provider settings, and tristan secret stores a credential in Windows Credential Manager. A secret is only ever typed at a hidden prompt. It is never an argument, never printed and never logged.

tristan config list                         # every setting, its value and its default
tristan config get ollama.model
tristan config set ollama.model llama3.1
tristan config unset ollama.model           # back to the default
tristan secret status                       # set / not set, never the value
tristan secret set azure-openai-key         # typed at a hidden prompt
tristan secret delete azure-openai-key

The settings are ollama.host, ollama.model, azure.endpoint, azure.deployment, azure.apiVersion, bedrock.region, bedrock.model, bedrock.profile and copilot.model. Each value is checked before it is saved, with the provider’s own rule where it has one. kidsMode, allowRules and every other key are refused, so the terminal cannot switch kids mode off or grant approvals. The only secret name is azure-openai-key: on Windows, Bedrock uses the AWS CLI’s own credentials.

After installing a tool with winget or npm, open a new terminal so it is on your PATH. None of the five providers has been run against a live account on Windows yet. See What is supported.

Run a mission

cd C:\code\my-project
tristan run "explain this project"                              # Ollama is the default provider
tristan run --provider claude "fix the failing test"
tristan run --provider azure --folder C:\code\other "add a README"

Log lines print as > text and code streams to standard output. Status lines ([...]) and failures go to standard error, and the run ends with Done: ... or Failed: .... Everything shown comes from a model or a tool, so terminal control sequences in it (screen clearing, cursor moves, clipboard writes) are shown escaped, never obeyed. Press Ctrl+C to cancel. Tristan stops the provider and every process it started, prints Cancelled and exits with 130. A second Ctrl+C exits at once.

Approvals in the terminal

Default

Ask

Every action that needs approval stops and asks: [y]es / [n]o / [a]lways. Anything other than y, yes, a or always is a no.

--yes-routine

Auto

Routine actions run without asking. Anything else still asks.

--yolo

Yolo

Nothing asks. Use it only in a folder you can afford to lose. It cannot be combined with --yes-routine.

  • Always allow stays narrow. a saves a rule for a plain program name or a file edit inside the working folder, as on the Mac. Rules live in %APPDATA%\Tristan\settings.json and apply only in later runs that have a terminal.
  • Commands run in PowerShell. The model’s run_command runs pwsh if it is installed, otherwise powershell.exe, with -NoLogo -NoProfile -NonInteractive -Command.
  • Windows-aware rules. Auto never runs, and Always never remembers, a risky PowerShell program (Remove-Item, del, iex, Invoke-WebRequest, Start-Process, reg, Import-Module and over a hundred other names, in any letter case and with a program extension such as .exe, .cmd or .ps1). The same goes for a command with an operator or a PowerShell construct (;, &, |, >, backtick, $, { }, (, [, -EncodedCommand and its abbreviations) or with invisible Unicode separators. The Approvals guide has the Mac rules these extend.
  • Folder checks compare real paths. They ignore letter case (drive letters included) and treat \ and / the same. A UNC path only matches its own share, and junctions and symbolic links are resolved first. C:\Work\Proj-evil is not inside C:\Work\Proj.
  • No terminal, no approvals. With input piped or redirected, every action that needs approval is denied, saved rules are ignored, and the run exits with 3. For unattended runs, choose --yes-routine or --yolo on purpose.

Exit codes

What tristan returns
CodeMeaning
0The mission finished (or the command succeeded).
1The mission failed or ended without finishing, a setting could not be saved, or a wrong PIN for kids, config or secret (for run --allow-cloud it is 2).
2Usage error: bad arguments, an unknown setting, a refusal in kids mode, or no terminal where one is needed.
3The mission ended but at least one action was denied. Denied wins over failed, because a denial usually causes the failure.
130Cancelled with Ctrl+C.

Kids mode

The same kids mode as the Mac app (the same kidsMode setting and parent PIN). While it is on, only Ollama answers, and every action asks.

tristan kids set-pin       # 4 or more digits, typed without echo; asks for the current PIN first
tristan kids on            # needs a PIN to be set first
tristan kids status
tristan kids off           # asks for the parent PIN
tristan run --provider claude --allow-cloud "help with homework"   # a parent allows one cloud run with the PIN
  • In kids mode a cloud provider is refused unless a parent types the PIN with --allow-cloud for that one run. --yes-routine and --yolo are refused. tristan config set|unset and tristan secret set|delete also ask for the PIN.
  • Every PIN check waits 1.5 seconds, right or wrong, so guessing from a script is slow and the timing gives nothing away.
  • Fails closed. If settings.json exists but cannot be read, kids mode counts as on and nothing is saved until the file is repaired.
  • Honest limits. A child at the keyboard can answer the approval prompts. The PIN is stored as an unsalted SHA-256 hash in Credential Manager (com.tristan.app/kids.pin), as on the Mac. And the settings file is not a lock against someone who uses the same Windows account: they can edit it or delete the credential. The kids-mode lock on the Mac app uses the Mac’s own login as well; see Kids safe mode.

History and sessions

tristan history                              # past missions, newest first
tristan history --query readme --status done
tristan history --rerun 2                    # run line 2 again (Ask mode, same provider and folder)
tristan history --rerun 2 --folder C:\code\x # if that folder is gone
tristan sessions                             # missions running now, from any terminal

History is kept in %APPDATA%\Tristan\history.json. Besides the provider, folder and status, only the task and a summary of up to 240 characters are stored, never the streamed code. A re-run never quietly switches folders: if the original folder is gone, it stops and asks for --folder. Running missions register in %APPDATA%\Tristan\sessions. Entries whose process has ended are skipped and removed.

Git Bash and mintty

Use Windows Terminal, PowerShell or cmd. In mintty, the window Git Bash opens by default, a program’s input is a pipe, not a console, so tristan sees no terminal. Every approval in Ask mode is denied, and kids set-pin, kids off and secret set refuse. Code review found this, and no test has run it. A related known gap: input redirected from NUL may look like a terminal, so saved always-allow rules would apply, while every prompt still reads nothing and denies.

Uninstall

If you used the installer, uninstall in Settings, Apps (or Add or remove programs). That removes the program files and the PATH entry. It keeps your settings and history in %APPDATA%\Tristan and your stored secrets in Credential Manager. To remove those as well, run the first three lines below before you uninstall (the tristan command is gone afterwards):

tristan secret delete azure-openai-key                 # if you stored a key; repeat for any other key you stored
cmdkey /delete:com.tristan.app/kids.pin                # the parent PIN hash, if you set one (form checked in CI on a made-up entry)
Remove-Item -Recurse "$env:APPDATA\Tristan"            # settings, history and the sessions folder
Remove-Item -Recurse "$env:LOCALAPPDATA\Programs\Tristan"   # only if you used the zip and unpacked it here

If you used the zip, also remove its folder from your user PATH (Settings > System > About > Advanced system settings > Environment Variables). Ollama, the provider CLIs and their logins are not touched.

Part 2

How we ported it

The design rule was one core, no fork. The Mac app, the iPhone app and the Windows command use one copy of the agent loop, the providers and the approval logic. The Windows version must never run weaker safety than the Mac.

The TristanCore split

  1. Pin today’s behaviour first. Before any code moved, a new test suite pinned the Mac’s approval policy and sandbox, so later changes could not quietly weaken them.
  2. Split the package. The portable code moved into a library, Sources/TristanCore: the agent loop and tools, the five providers, approval types and policy, settings, history and session memory. Code that starts processes or opens sockets lives in Sources/TristanCore/Processes, which the iPhone app does not compile.
  3. Add the command. Sources/TristanCLICore holds the commands (run, providers, config, secret, kids, history, sessions), and Sources/TristanCLI is a thin main. The product is tristan on Windows and Linux and tristan-cli on macOS, because the Mac’s case-insensitive file system would mix up tristan with the app’s Tristan binary.
  4. Keep the Mac app where it was. Sources/Tristan (AppKit and SwiftUI) and Sources/Tristan/Shared (themes, Markdown rendering and the iPhone link, which need SwiftUI or Apple’s Network framework) are declared in Package.swift only on macOS, so Windows never tries to build them.

What stayed Mac-only

Everything in Sources/Tristan: the HUD window and notch overlay, voice, the wake word and spoken lines, Spotify, notifications, launch at login, the offline fallback to Ollama, the DEMO provider, and the server side of the iPhone remote. Also everything in Sources/Tristan/Shared: themes, the Markdown renderer and the iPhone link client. The Mac app’s behaviour and tests were kept unchanged throughout. Where a change touched both platforms, the commit says so (for example the stricter Copilot carriage-return handling and the ExitWatch change).

Part 5 · Building in the open

How we build

This port is an experiment in building in the open. The design spec, the plan and the spike notes are in the repository. The review findings and the rulings were kept in a working ledger that is not in the repository; this section summarises it and tells the story as those records show it, including the parts that went wrong. When we say “we”, we mean the maintainer and the AI coding agents working under written rules.

The process

  1. A backlog issue. Issue 23 (Windows support), which shares its core work with a command-line version (24) and Linux (22).
  2. A brainstormed design spec. Goals, non-goals, anti-goals (“a Windows build that silently runs weaker safety than the Mac”, “forking the core”, “secrets in plain text files”), findings from the code, and the open questions with the decisions taken. The maintainer decided: terminal first, and all five providers required.
  3. A written plan of 20 tasks (Task 0 to Task 19), each with its files, interfaces, tests to write first, and commit message, plus five review focus points: Windows paths, drive roots, PowerShell syntax, arguments through .cmd shims, and Ctrl+C killing the whole tree.
  4. Subagent-driven development. Each task went to a fresh implementer agent with a brief cut from the plan. A separate reviewer agent then checked it against the spec and for quality. Fix rounds were capped at five. Decisions that changed the plan were recorded as rulings (R1 to R17) in the working ledger, with the reason and the cost if wrong.
  5. A real Windows machine in the loop. The agents could not reach a Windows PC. For the first eleven tasks, Windows-only code was written behind compile guards and never compiled. Then the maintainer allowed GitHub Actions windows-latest to be the Windows machine, and every later task had to go green there. That loop is slow: a Windows CI run took from about 3 minutes early on (compile failures) to about 20 minutes once the smoke test and the zip checks were added, so each fix waited on a pipeline. With a Windows PC in reach, the agents could have compiled and run the tests locally in a fraction of that time, and most of those waits would have gone away.
  6. A final whole-branch review with at most one fix wave, then the hand-off. The review found one critical problem (the committed iOS project had not been regenerated after new core files were added, so the iPhone app did not compile) and four important ones; the one fix wave addressed them.

Bugs the reviews and the Windows runner caught

Every one of these was found before the first release. Each is summarised from the working ledger or a task report, neither of which is in the repository; the fixes are in the commits.

Real problems found during the port, and what changed

PowerShell expression modeReview of Task 8A first word such as -join, return, a digit or using starts an expression or statement, not a program, and could have been saved as an Always rule. Program names must now start with a letter, and keywords are on the never list.
Unicode separatorsReview of Task 8Characters such as U+2028 and U+0085 could act as hidden statement separators. Any control, format or non-ASCII space character now makes a command ask.
Port takeoverReview of Task 9After the host died, a rogue listener on the same port could have answered “allow”. A second token now lets the shim check the host as well.

Process lessons, honestly

  • A shared GitHub login is shared state. Several agents share one machine. Something outside one agent’s session switched the global gh account to another login, and that agent stopped before pushing. Each command now passes its own token for the repository owner’s account.
  • Agents over-claim. One implementer reported 516 tests when the reviewer counted 354. Another wrote in its report that the maintainer had asked for a commit to main, which never happened. Both claims were checked, recorded as unsupported and ignored. Test totals on this page come from CI logs and reviewer runs.
  • Red first, not always. Some tasks wrote their tests alongside the code instead of watching them fail first, and one guard test passed on the old code too. The reports say so.
  • Scope corrections are normal. A ruling first listed three AWS secret names next to the Azure key for tristan secret. Review showed that only the iPhone app reads them, so they were dropped.
  • Commit trailers drifted. For a stretch, commits named a different model in their co-author line than the rest of the branch. History was not rewritten; the working ledger notes it.

Build, test and package from source on Windows

  1. Install the toolchain. CI uses Swift 6.4.2 (swift-6.4.2-RELEASE, target x86_64-unknown-windows-msvc). Install Swift for Windows following swift.org’s instructions, including Visual Studio or its Build Tools with the C++ tools and a Windows SDK. The packaging script also needs dumpbin.exe from Visual Studio, and PowerShell 7 (pwsh). The CI image (win25-vs2026) has Visual Studio preinstalled.
  2. Clone and build. Use a normal terminal, not Git Bash.
git clone https://github.com/mariotristan/jarvis-tristan.git
cd jarvis-tristan
swift --version                              # CI: Swift version 6.4.2 (swift-6.4.2-RELEASE)
swift build --product tristan
swift test --filter TristanCoreTests
swift test --filter TristanCLITests
& (Join-Path (swift build --show-bin-path) 'tristan.exe') providers
pwsh -NoProfile -File scripts\package-windows.ps1 -Version 0.0.0-local   # dist\Tristan-0.0.0-local-windows-x64.zip and .sha256
pwsh -NoProfile -File scripts\package-windows-installer.ps1 -Version 0.0.0-local   # then the installer from the same files: dist\Tristan-0.0.0-local-windows-x64-setup.exe and .sha256

Before you run the tests on your own PC: two tests use a real az and aws if they are installed. The Azure one asks az for an access token when you are logged in (it checks the token is not empty and does not print it). The AWS one uses made-up keys against a closed local port. Some tests also write to, and then restore, your Credential Manager entry for the Azure key. Run them under an account without real credentials if you prefer.

The Mac app is not built on Windows: Package.swift declares the Tristan app and its tests only on macOS. On a Mac the command is tristan-cli and needs the full Xcode (DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer swift build).

How CI is wired

.github/workflows/windows.yml runs on pushes to main, on pull requests and by hand. It is one of the four checks main requires. It has a read-only token (permissions: contents: read), checks out without keeping credentials, uses no secrets, and pins every action by commit (the Swift setup action’s own internal steps are not pinned). A newer push cancels an older run on the same branch.

How releases are cut

  1. Push a tag v* (for example v1.2.3). Only the maintainer does this. v0.6.2 is the latest tag so far.
  2. Secret scan. gitleaks over the whole history. A leak stops the release.
  3. Windows job (read-only token): the same toolchain pins, both test suites, then the version. The leading v is dropped, and every character other than a letter, digit, dot or dash becomes a dash, case-sensitively (v1.2.3_rc1 gives 1.2.3-rc1; a bare v gives 0.0.0). It packages, unpacks into a clean folder, checks --version, the checksum and the notices, builds the installer from the same files and runs the installer test on it, and uploads the zip and the installer. A version that still does not start with a letter or digit (the tag v-1) stops it.
  4. Mac job (macos-15, Xcode 16.2): runs swift test and builds the DMG with the tag as its version. It waits for the Windows job, downloads the zip and the installer, and creates one GitHub Release with generated notes, the DMG, the zip, the installer and a SHA-256 for each.

The release workflow has run twice with the Windows job. Run 42409091093 succeeded for v0.6.0 (the zip and the DMG). Run 42425315224 succeeded for v0.6.1, the first release with the installer: it built the installer and ran the same installer test as the Windows workflow before publishing. The Windows steps are the same lines the Windows workflow runs on every push with made-up tags, such as v1.2.3_rc1; other tag shapes have only been tried in that workflow. (Counted as a snapshot on 7 November 2026, release.yml has six successful runs in all; the four before v0.6.0 were Mac-only releases from before the Windows work.)

What CI cannot prove

  • Live logins and services: real Claude Code (including whether it passes the MCP env block), the real Copilot CLI, az login tokens against Azure OpenAI, Bedrock with real AWS credentials, a real Ollama.
  • A person at a console: typing y / n / a, the echo-free PIN prompt, Ctrl+C through the console handler, how NUL and mintty look to the terminal check.
  • Desktop Windows: CI runs Windows Server 2025; Windows 10 and 11 desktop editions have not run it.
  • The installer’s wizard: only silent installs and uninstalls run in CI, including inside the release workflow that built the released installer. Nobody has clicked through the wizard, seen the final uninstall message, or seen what SmartScreen says about the unsigned setup.
  • A pristine Windows install: the runner has the Swift toolchain and the Visual C++ runtime installed, so “runs from the installer or the zip on a fresh PC” is strong evidence, not proof. The released installer and zip were only inspected on a Mac, and SmartScreen’s reaction to the unsigned files has not been seen.
  • Other environments: consoles with a non-UTF-8 code page, Credential Manager under an interactive or roaming profile or enterprise policy, UNC working folders, case-sensitive folders, drives without 8.3 names, ARM64.

What we would do differently

Our own view, drawn from the working ledger and the reviews:

  • Put the real platform in the loop first. Eleven tasks of Windows code were written blind behind compile guards, and the first Windows compile failed in ways no Mac review could catch. A Windows CI job on day one would have caught them sooner.
  • Tests that start tools must use fakes. A launcher that searches PATH can reach a real CLI (on a Mac Homebrew's folder comes first), so no test, script or agent may run anything that launches a real aws, az, claude, copilot or ollama: tests start fake programs by absolute path only, with a clean PATH and environment.
  • Give each agent its own credentials instead of sharing one global gh login between parallel agents.
  • Hold the line on red-first tests, and verify every number an agent reports before it reaches a page like this one.
