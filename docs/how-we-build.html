How T.R.I.S.T.A.N. gets built.

The Mac app came first, in one long day. Then the iPhone and iPad remote, the kids safe mode, the offline fallback and the Windows terminal version. This page has the timeline, notes on the Mac app, and the rules we follow so anyone, person or coding agent, can pick the work up.

Part 2

Notes on the Mac app

The Mac app is the original. Everything else (the iPhone remote, the Windows command, the site) came after it and borrows from it.

What it is

  • A native macOS app in Swift: a SwiftUI HUD window plus AppKit for the notch overlay, the menu bar item, the global hotkey and full screen.
  • It needs an Apple Silicon Mac and macOS 14 or later. The DMG is ad-hoc signed, not notarized, and there is no auto-update yet (issues #7, #8 and #9).
  • It does not replace an agent. It runs Claude Code, Copilot, Amazon Bedrock, Azure OpenAI or a local Ollama model, shows what they are doing, and asks you before each action.
  • The Mac app is the most complete version: voice and the wake word, Spotify control, kids safe mode, 32 themes, the offline fallback and the server the iPhone app connects to.

The order it was built in

  1. A HUD that looks right and a safe loop. The first commit already had the HUD, the notch, approvals and a DEMO provider, so there was always something to run without an account.
  2. Safety next. Per-action approvals, approval modes and narrow “always allow” rules came in the first twenty minutes, before most providers.
  3. Providers one by one, each behind the same interface: Claude Code, Bedrock, Azure OpenAI, Copilot, then Ollama.
  4. Packaging and CI early. The DMG and the workflows were in place before the first release.
  5. The phone, the kids and the polish. The iPhone and iPad remote, kids safe mode, themes, sound, the demo recorder and the website.
  6. Windows last, by splitting the portable core out of the Mac app (How we ported it).

No design spec for the Mac app. It grew from the first commit, with its reasons in commit messages and issues. The iPhone and iPad remote has a written design (docs/superpowers/specs/2026-11-06-ios-remote-design.md) and the Windows port has a spec, a plan and spike notes in the same folder.

What Windows reuses

The Windows version runs the same TristanCore as the Mac: the agent loop, all five providers, the approval rules, history and kids routing. Getting there meant moving code out of the Mac app into the core, behind small seams for settings, secrets and starting processes, with the Mac approval policy pinned by tests first so the move could not weaken it. The HUD, the notch, voice, the wake word, Spotify and the iPhone link stay Mac-only for now. The Windows window is a backlog of its own (#32).

What is still missing

  • Notarization and auto-update (#7, #8), and an Intel build (#9).
  • Live checks of several things that only have fake-backed tests: Bedrock against real AWS, Copilot’s ASK mode, the wake word, notifications and the notch on a real session (#1, #4, #5).
  • The version number is not shown in the Mac app yet (#84).
  • The full list is on the backlog page.
Part 3

The rules we follow

These keep the project honest and easy to pick up. The full version, with the page template, the checklists and the pull request flow, is the site guide.

  1. Say what was checked. Every claim says what ran, where, and what did not. The status labels (verified in CI, checked by hand, needs a live-account check, not on this platform) are used strictly.
  2. Real dates and numbers. Counts, versions and times come from the repository, and every place that repeats them is updated together.
  3. Nothing private in public. No secrets, accounts, machine names, employers or clients in pages, commits, issues or screenshots.
  4. Pull requests only. main is protected. Docs-only pull requests skip the build jobs. Tags and releases happen only when the owner decides.
  5. Tests never start a real provider tool. They use the fakes in scripts/ci/fakes.
  6. Plain, accessible pages. Hand-written HTML, no framework, no external scripts, readable on a phone and with a keyboard.
  7. Quality over loudness. Audio is measured, never assumed, and a person listens before it is called done.
